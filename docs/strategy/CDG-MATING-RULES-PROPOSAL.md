## 1. What was measured, and where the boundary is

| | |
| :-- | --: |
| Public cartridges in the Commons | 500 |
| Cartridges read here (in-tree `projects/*/project.json`) | **466** |
| Public cartridges out of scope (git submodules, not read) | 34 |
| Client-private cartridges read | **0** |
| CDG interfaces declared across those 466 | **888** |
| Interfaces resolving to a known standard family | **251** (28.3%) |
| Interfaces declaring `internal` (private geometry, correctly inert) | 516 |
| Interfaces naming an external standard the normalizer does not recognise | 119, over 88 distinct strings |
| Objects carrying at least one family-resolved interface | **196** |

The derivation reads only manifests **committed to this repository**: every `projects/*` path
declared as a submodule in `.gitmodules` is skipped whether or not it is checked out, and the
client-private slugs are named a second time in the script. CI checks out submodules recursively
and a developer usually does not, so a "is a manifest on disk" rule would have made the committed
artifact unreproducible *and* would have read cartridges we have no right to publish. The price is
34 public submodule cartridges out of scope this pass — see §7.

## 2. The baseline: how empty the graph actually is

The service's own rule, replayed over exactly those 466 manifests:

| Measure | Today |
| :-- | --: |
| Graph nodes (objects with a resolved standard family) | 196 of 466 — **270 objects can hold no edge at all** |
| Edges (distinct object pairs) | **225** |
| Isolated nodes (in the graph, degree 0) | 65 of 196 |
| Density over graph nodes | **1.177 %** |
| Density over the whole catalogue | **0.208 %** |

Two notes on those figures. First, `get_graph()` reports **229** edges, not 225: it keys edges by
`(pair, family)`, and four object pairs mate in two families each. Distinct object pairs is the
right denominator for density, so that is what is used throughout. Second, the "~93 % empty" figure
in [`CDG-ACTIVATION-STRATEGY.md`](CDG-ACTIVATION-STRATEGY.md) was counted against **22**
`compatible_with` links across 17 objects. The manifests have moved a long way since: there are now
420 `compatible_with` references, **249 of which name two in-scope public cartridges**. That
changes the shape of the problem, and §6 is the consequence.

## 3. Method, and the held-out answer key

Each candidate rule is one claim:

> objects declaring standard family **S** in role **A** mate with objects declaring **S** in role **B**

Interfaces are grouped by standard family — using `normalize_family()` from the live graph, not a
second copy of it — and by role, which is the manifest's `geometry_type`, restricted to the 14 names
the shared interfaces vocabulary marks canonical for Yantra4D (`socket`, `profile`, `bolt_pattern`,
`snap`, `pocket`, `surface`, `thread`, `flange`, `grid`, `rail`, `custom`, `spline`, `boss`,
`fem_mesh`). No new role names were invented. Unrecognised standards, `internal` and `none` are
excluded before any rule is formed, so a rule can never rest on private geometry.

That yields **89 candidate rules** over the 251 family-resolved interfaces.

The scoring uses a signal the rule generator never consumes: the cartridge authors' own
`compatible_with` lists. Those 249 in-scope pairs are hand-written assertions that two specific
objects mate. They are a **held-out answer key** — a rule is scored by how many of them it explains,
never generated from them. The baseline graph explains **136 of 249 (54.6 %)**; it misses 113 pairs
the authors already vouched for.

Confidence tiers, and what earns them:

| Tier | Rules | Earned by |
| :-- | --: | :-- |
| **corroborated** | 24 | ≥2 author-declared links assert this exact family+role pairing, and both roles have ≥2 objects |
| **plausible** | 43 | exactly one corroborating signal: a single author-declared link, or the live graph's own table already admitting the pairing |
| **speculative** | 22 | co-declaration of a standard family and nothing else |

A rule whose either side has only one object is marked `one_sided` and can never reach
**corroborated**: one object is a fact, not a rule.

The single strongest cross-commons rule is not in that top five: `webbing-strap` · `rail` ↔ `snap`
adds only 1 edge, but its members are consumed by **11 Fashion Cabinet objects** across the bridge —
a mating rule that also explains bridge links is doing double duty, and this one does.

Two structural findings sit underneath the table:

- **`profile` ↔ `profile` is the missing self-mating role.** Four of the top five are the same shape.
  The live table self-mates `bolt_pattern`, `grid`, `rail`, `thread`, `snap`, `socket` — but not
  `profile`, and `profile` is how the commons spells a dovetail, a gear tooth, an extrusion section
  and a belt tooth. Arca-Swiss is *entirely absent* from the graph despite seven author-declared
  links, purely because of that omission.
- **`bolt_pattern` ↔ `thread` is the missing complementary pair.** A plate with 1/4-20 holes and a
  stud with a 1/4-20 thread join through a screw neither of them contains. Eleven authors have said
  so; the table has not.

### Falsification gate per rule

No rule should be ratified on counts alone. Each gets a check that could **prove it wrong** — a
dimensional assertion the render sandbox can make (`apps/api/tests/scripts/verify_design.py` already
does watertightness, bounding-box `dimensions` and `collision` checks against rendered STLs), or a
constraint expressible in the manifest `constraints` block (`{"expression": …, "severity": "error"}`).

| Rule | Falsifier — the rule is wrong if this fails |
| :-- | :-- |
| `unc-1/4-20` `bolt_pattern`↔`thread` | **Dimensional, sandbox.** Render both at declared defaults; the threaded side's major Ø (`quarter20_d`, nominal 6.35 mm) must pass the hole side's `face_hole_d` with clearance, and `thread_len` must not exceed the receiving `quarter20_depth`. **Manifest gate:** reject any member declaring the 1/4-20 family whose interface parameters carry no diameter within 6.35 ± 0.35 mm. |
| `arca-swiss` `profile`↔`profile` | **Polarity, and it is the weak point.** `profile` hides male/female: two Arca *plates* must NOT mate, only plate↔clamp. Falsifier: a sandbox `collision` check on the two cross-sections — interlock passes, interpenetration fails. **Manifest gate:** require the interface to declare polarity before the edge is drawn; today it must be inferred from the label, which is not evidence. |
| `involute-gear` `profile`↔`profile` | **Dimensional + axis.** `module`/`m` and `pressure_angle` must be equal — necessary but *not sufficient*: the current members are a bevel pair, a planetary stage and a worm wheel, and a bevel gear does not mesh with a spur gear on parallel axes. Falsifier: equal module and pressure angle **and** a declared compatible axis arrangement; absent that declaration the rule is unproven. |
| `t-slot-extrusion` `profile`↔`profile` | **Dimensional.** Slot width and module must match. This family currently absorbs the string `T-slot / 3/4in miter` alongside `2020/2040 extrusion (20 mm module, 6 mm slot, M5)` and `OpenBuilds V-slot` — falsifier: require a declared slot width on both sides and reject any cross-width pair. A failure here falsifies the **family normalization**, not just the rule. |
| `timing-belt` `profile`↔`profile` | **Dimensional.** Pitch must be equal (GT2 2 mm ≠ HTD 3M ≠ HTD 5M) and `belt_w`/`belt_width` ranges must intersect. Falsifier: parse the pitch out of the declared standard string and require equality; a GT2↔HTD 5M edge falsifies the rule. |

The same instrument generalises: for any ratified rule, render both members at their declared
defaults and assert the male envelope seats in the female envelope with the declared clearance. That
is the difference between a graph that claims compatibility and one that has checked it.

**Read the last two columns together.** T3 adds 74 edges — more than T1 — and explains **not one

for gating it behind the dimensional checks in §4 if it is ratified at all.

## 6. The larger finding: the graph ignores what the authors already wrote

`compatible_with` appears 420 times across the manifests, naming **249 pairs of in-scope public
cartridges**. `compatibility_graph.py` never reads the field — it is mentioned once in the module
docstring and nowhere in the code. Those are not derived edges; they are hand-authored assertions
that two named objects mate, already reviewed and already committed.

Ingesting them is a different mechanism from a mating rule and is listed separately for that reason:

| | Nodes | Edges | Isolated | Density over its nodes |
| :-- | --: | --: | --: | --: |
| baseline | 196 | 225 | 65 | 1.177 % |
| **+ author-declared links** | **249** | **338** | **38** | 1.095 % |

Density *falls* because the node set grows faster than the edge set: 53 objects have an
author-declared partner but no recognised standard family, so they are invisible to the graph today
and would become nodes. Coverage is the better measure — connected objects rise from **131 to 211**,
and 113 pairs the authors already vouched for stop being missing. It carries no derivation risk,
because nothing is derived.

Ninety of the 249 declared pairs share no resolved standard family at all, so **no family+role rule
can ever reach them.** Those need either normalization work or this ingestion path.

## 7. Known limits of this derivation

- **`internal` is 58 % of all declared interfaces** (516 of 888). Those objects are structurally
  unreachable by any standards-based rule. Density will stay near 1–2 % until manifests name shared
  standards where they genuinely have them.
- **The largest unrecognised standard is the cross-commons seam.** `iso_8559` (body measurements)
  appears on 28 interfaces across `body-form`, `figure-child`, `garment-stand` and `lingerie-form` —
  and Fashion Cabinet pins a `yantra4d-body-form.snapshot.json` against exactly those. It is a
  *measurement* standard, not a mechanical one, so whether it implies mating is precisely an
  operator ruling, not an inference this derivation should make.
- **The normalizer silently drops real members.** `tripod-hub` declares
  `1/4"-20 UNC — major Ø6.35 mm, pitch 1.27 mm, minor Ø4.976 mm` and does not match the `1/4[\s-]?20`
  pattern because of the inch mark. It is invisible to the 1/4-20 family today. There are 88 distinct
  unrecognised standard strings; this is the one confirmed to be a plain miss.
- **First-match-wins family patterns can over-merge.** `T-slot / 3/4in miter` lands in
  `t-slot-extrusion` rather than `miter-ttrack` because of pattern order. Rule 4's falsifier is
  therefore also a test of the family table.
- **34 public submodule cartridges are out of scope**, and 38 `compatible_with` references point at
  them. Extending the scan to a committed public-cartridge snapshot would close that without ever
  reading a private manifest.

## 8. Operator ask

**Which of these rules imply mating, and may be ratified?** Concretely: (a) ratify or reject
**T1, the 24 corroborated rules** as a block — +64 edges, author-declared recall 54.6 % → 59.8 %,
each with the falsifier in §4 attached as its acceptance test; (b) rule specifically on the two
structural claims underneath T1, since they are what actually generalise — that **`profile` self-mates**
within a family (this alone unblocks Arca-Swiss, involute gears, T-slot and timing belts, seven
author-declared links currently producing no edge), and that **`bolt_pattern` ↔ `thread` mates**
through a fastener neither object contains; (c) decide whether the graph should **ingest the 249
hand-authored `compatible_with` links** as edges in their own right — the largest single coverage
gain available, 131 → 211 connected objects, with no derivation risk; (d) rule on whether
**`iso_8559` implies mating** across the Fashion Cabinet seam, or is a measurement standard that must
never draw an edge; and (e) confirm that **T3 stays unratified** until each of its rules carries a
passing dimensional check, on the evidence that it adds 74 edges and explains zero additional
author-declared pairs. T2 is deliberately left for a later pass: it is small (+12 edges) and mostly
one-sided, and nothing depends on it.
